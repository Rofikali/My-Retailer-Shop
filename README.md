# RetailShop ERP

Single-tenant internal ERP for one retail shop. Nuxt 4 (TypeScript) + Postgres (Drizzle ORM). See
[`docs/00-README.md`](docs/00-README.md) for the full PRD/HLD/LLD/ERD/Design Patterns/SDLC/Testing/DevOps/
Security doc set this codebase implements — start there before making architectural changes.

## Status

Every core module is implemented, not stubbed: Cash Book, Sales, Purchases, Inventory, Expenses, Customers,
Suppliers, Admin (Users, Data Quality/Audit Log, Business Settings), all 4 financial reports, and the
Dashboard — each following the same pattern (repo → service, owning the DB transaction → API → page), with
`LedgerService` as the single append-only source of truth every one of them posts through.

**Not yet done, and worth knowing about:**
- **Nothing here has actually been run.** No `npm install`, no live Postgres, no browser — this was all
  written and syntax-checked (`node --check` on every `.ts` file, plus every `.vue` file's script block)
  in a sandbox with no network access. Treat it as reviewed-but-unexecuted code, not verified code, until
  you've run `pnpm run test:all` yourself against a real database.
- **E2E tests are written but not run or wired into CI** — see `tests/e2e/critical-flows.spec.ts` and the
  note at the bottom of `.github/workflows/ci.yml`.
- **No approval workflow, no double-entry Journal/GL usage** — both are optional extension points, not
  gaps in the core system (see `docs/07-SDLC-Process.md` Phase 3 and the Journal/General Ledger page
  comments).

## Setup

```bash
# 1. Install dependencies
pnpm install

# 2. Start Postgres locally
docker compose up -d

# 3. Configure environment
cp .env.example .env
# edit .env if you changed any docker-compose defaults

# 4. Generate and run the first migration
pnpm run db:generate
pnpm run db:migrate

# 5. Seed the chart of accounts + an owner user
#    (uses SEED_OWNER_EMAIL / SEED_OWNER_PASSWORD env vars if set, otherwise
#     owner@example.com / ChangeMe123! — change this password after first login)
pnpm run db:seed

# 6. Run the dev server
pnpm run dev
```

Then log in at `http://localhost:3000/login`.

## Troubleshooting

**`ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` on `pnpm install`**
pnpm v11 defaults to refusing packages published in the last 24h (`minimumReleaseAge: 1440`), as
protection against a compromised package being published and immediately pulled in. This repo ships
`pnpm-workspace.yaml` with `minimumReleaseAge: 0` to disable that for local dev — if you still hit this,
confirm that file exists at the project root and re-run `pnpm install`. Consider raising the value back up
(e.g. `1440`) once you're closer to a production deploy, for the actual supply-chain protection.

**`Error: DATABASE_URL is not set` when running `db:migrate` / `db:seed`**
Two possible causes, check both:
1. You haven't copied the env file yet: `cp .env.example .env` (do this once, before step 4 in Setup).
2. If `.env` already exists and you still get this: it's an import-order bug — `dotenv/config` must be the
   *first* import in any script that reads `process.env` at module load time (ES module imports execute
   top-to-bottom; if something that reads `process.env.DATABASE_URL` imports before `dotenv/config` runs,
   the env var isn't loaded yet). Already fixed in `migrate.ts`/`seed.ts`/`drizzle.config.ts` in this repo —
   keep this rule in mind if you add new scripts under `server/db/`.

**`vitest run` fails with `Cannot find module './.nuxt/tsconfig.json'`**
`.nuxt/tsconfig.json` is generated by Nuxt itself (on `nuxt dev`, `nuxt build`, or `nuxi prepare`) — it
doesn't exist right after a bare `pnpm install`. This repo's `postinstall` script runs `nuxt prepare`
automatically so this shouldn't happen on a fresh install — if you already ran `pnpm install` before
pulling this fix, run `pnpm install` again (or `pnpm exec nuxi prepare` directly) to generate it once.

## Testing

Three layers, matching `docs/08-Testing-Strategy.md`:

**1. Unit tests** — no dependencies, always fast, run these constantly:
```bash
pnpm run test
```
`tests/unit/ledger.service.test.ts` is the single most important test in the codebase — it verifies that
an unbalanced set of ledger lines is rejected. Everything else depends on this rule holding.
`tests/unit/validation.test.ts` covers the zod schemas (e.g. a credit sale requires a customer).

**2. Integration tests** — hit a real (isolated) Postgres, verify actual transaction/ledger behavior:
```bash
# One-time setup: create the test database
# The docker-compose init script (docker/initdb/) only runs on a FRESH volume. If
# you already have retailshop running, create the test DB manually instead:
docker compose exec postgres psql -U app -d retailshop -c "CREATE DATABASE retailshop_test;"

# Run migrations against the test DB (uses TEST_DATABASE_URL from .env)
DATABASE_URL=$TEST_DATABASE_URL pnpm run db:migrate

pnpm run test:integration
```
Highlights:
- `tests/integration/reports.test.ts` — seeds a known, hand-calculated set of transactions (capital, a
  credit purchase, a credit sale, an expense) and asserts every report matches exactly, including that the
  Balance Sheet actually balances.
- `tests/integration/sales.service.test.ts` / `purchases.service.test.ts` / `cashbook.service.test.ts` /
  `expenses.service.test.ts` — verify each Unit-of-Work posts the right ledger lines and rolls back
  completely on failure.
- `tests/integration/data-integrity.test.ts` — regression tests named after the specific real bugs found
  in the original Excel workbook (duplicate customer IDs, unbalanced postings, editable ledger rows).

**3. E2E tests** — a handful of critical flows against a real running app:
```bash
pnpm exec playwright install chromium   # one-time
docker compose up -d && pnpm run db:migrate && pnpm run db:seed
pnpm run dev   # separate terminal, leave running

pnpm run test:e2e
```

Run everything except E2E in one command:
```bash
pnpm run test:all
```

## Deployment

`Dockerfile` builds a production image (multi-stage: install → build → slim runtime). Migrations are
deliberately **not** run automatically on container start (see the comment in `Dockerfile`) — run
`pnpm run db:migrate` as an explicit CI/CD step before deploying a new image, per
`docs/09-DevOps-Deployment.md`.

`.github/workflows/ci.yml` runs on every PR: typecheck + unit tests always, integration tests against a
real Postgres service container. E2E is intentionally not wired into CI yet (see the comment at the bottom
of that file for why).

## Project layout

See `docs/04-LLD.md §1` for the full explanation. Short version:

```
app/          Nuxt pages, components, composables, middleware (frontend)
server/api/   Nitro route handlers — thin, no business logic
server/services/     Business logic, owns DB transactions
server/repositories/ The only place raw Drizzle queries live
server/db/    Schema, migrations, seed script
```

## Before you add a second real user

Read `docs/10-Security-and-Data-Integrity.md`. The auth in this scaffold is intentionally minimal
(hand-rolled session cookies) to keep the scaffold dependency-light — swap it for Better Auth or Lucia
before this holds anything beyond your own login.
