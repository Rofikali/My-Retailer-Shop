# Customer Ledger: Operating Guide and Controls

## Purpose

The **Customer Master** is the single, relatively static identity record for a customer. The **Customer Ledger** is the dynamic accounts-receivable history: every sale, opening balance, receipt, reversal, and approved metadata correction for that customer.

Use the ledger to answer three management questions:

1. How much does the customer owe now?
2. Which invoices, receipts, and adjustments created that balance?
3. Who entered, approved, or corrected each record, and why?

The ledger is not a free-form spreadsheet. Financial records are posted atomically to the party ledger and General Ledger, then retained as audit evidence.

## Why the Receipt Form Has Fewer Fields

The **Record Customer Receipt** form deliberately asks only for data that the cashier or owner knows at the time of collection:

| Receipt form field | Who supplies it | Ledger result |
| --- | --- | --- |
| Customer | User selects the existing Customer Master record | Customer ID and Customer Name are linked automatically. |
| Date | User | Posted as ledger Date. Default is today. |
| Amount | User | Posted as **Credit - Paid (Rs)**. |
| Payment Mode | User | Posted as Cash or UPI. |
| Reference No | User when available | Posted as Reference No; use UTR, bank receipt, or POS reference. |
| Remarks | User when needed | Posted as Remarks. |

The remaining columns must not be manually keyed during receipt entry because they are source-document keys, accounting values, calculated values, or audit values. The application creates them when the receipt is posted.

## Customer Ledger Column Dictionary

| Column | Source and rule | Editable after posting |
| --- | --- | --- |
| Date | Receipt date, sale date, or source transaction date. | No. Correct a financial/date error by reversal and reposting. |
| Voucher No | Generated receipt voucher such as `REC-XXXXXXXX`, or generated by the source transaction. | No. |
| Invoice No | Comes from a credit sale. A standalone receipt normally has no invoice number. | No. |
| Customer ID | Foreign key to Customer Master, selected before posting. | No. Never reassign a posted event to another customer. |
| Customer Name | Read from Customer Master using Customer ID. | Change contact/name details in Customer Master only. |
| Particulars | System description of the sale, receipt, or reversal. | Yes, as a controlled metadata amendment. |
| Debit - Owes (Rs) | Amount the customer owes, usually created by a credit sale or opening balance. | No. |
| Credit - Paid (Rs) | Amount received from the customer. A receipt amount posts here. | No. |
| Running Balance (Rs) | Calculated as prior balance + debit - credit, ordered by the ledger. | No. Never type or amend this value. |
| Payment Mode | Cash, UPI, or credit where applicable. | Yes, as a controlled metadata amendment. |
| Reference No | UTR, cheque, bank, POS, or external reference. | Yes, as a controlled metadata amendment. |
| Due Date | Due date from the source credit transaction. | Yes, as a controlled metadata amendment. |
| Status | `posted`, `amended`, or `reversed`. | No. System controlled. |
| Salesperson | Linked user from the sale when supplied. A direct receipt can be blank. | No after posting. |
| Remarks | Operational note. Never store card data, Aadhaar, PAN, passwords, or other unnecessary sensitive data. | Yes, as a controlled metadata amendment. |
| Entered By | Authenticated user who created the event. | No. |
| Approved By | Authenticated user who approved the event. | No. |
| Action | Owner-only control for amendment; it does not edit the original posted event. | N/A. |

## Receipt Posting Workflow

1. Create or verify the customer in **Customer Master**. Do not create duplicate customer records for repeat buyers.
2. Open **Customer Ledger** and select the customer by name and customer code.
3. For a customer payment, complete Date, Amount, Payment Mode, Reference No, and Remarks as applicable.
4. Select **Post Receipt** once only. The system creates a receipt voucher, a Customer Ledger credit entry, and balanced General Ledger postings in one database transaction.
5. Verify the voucher, credit amount, payment reference, and updated running balance in the ledger.
6. Use the receipt voucher and reference number when reconciling cash, UPI, bank settlement, and customer queries.

For a customer purchase on credit, use the **Sales** workflow rather than entering a receipt. Sales creates the invoice, debit/owes entry, inventory movement where applicable, and accounting records from the original source transaction.

## Amendments: Safe Metadata Correction

An amendment is appropriate only when the financial event is correct but descriptive metadata is wrong or incomplete.

### Allowed amendment fields

- Particulars
- Payment Mode
- Reference No
- Due Date
- Remarks

### Required control

1. An owner selects **Amend** on a posted customer-ledger row.
2. The owner changes only the allowed fields.
3. The owner enters a meaningful reason of at least 10 characters.
4. The system appends an amendment record with the owner and timestamp.
5. The ledger displays the latest approved metadata and marks the event `amended`.

### Locked fields

Date, voucher number, invoice number, customer, debit, credit, running balance, entered-by, approved-by, and status remain locked. The original record is retained and the correction history is never overwritten.

## Financial Errors: Reverse and Repost

Do **not** use Amend when the amount, customer, invoice allocation, transaction date, tax, discount, or payment allocation is wrong. These change accounting facts.

1. Create an authorized reversing entry linked to the original event.
2. Post a new, correct source transaction from Sales, Receipt, Cash Book, or the appropriate registry.
3. Reconcile the Customer Ledger, General Ledger, Trial Balance, Cash Flow, and inventory movement if applicable.
4. Retain the original document, reversal reason, and correction evidence according to the business retention policy.

This preserves period integrity, receivable aging, audit traceability, and management reporting.

## Management and CA Review Checklist

- Review overdue balances and credit limits before extending more credit.
- Reconcile daily cash and UPI receipts to receipt vouchers and bank/POS references.
- Investigate blank references for non-cash receipts.
- Review amended and reversed rows with their reasons and approving user.
- Compare customer-ledger totals with debtor control account balances in the General Ledger.
- Close accounting periods only after outstanding receipt, sales, reversal, and bank-reconciliation exceptions are resolved.
- Restrict owner access and review user activity regularly; never share owner credentials.

## Responsibilities

| Role | Responsibility |
| --- | --- |
| Cashier/operator | Records complete receipts promptly and attaches accurate references/remarks. |
| Salesperson | Creates sales from the sales workflow and provides invoice/source-document details. |
| Owner/approver | Reviews exceptions, authorizes corrections, performs amendments or reversals, and monitors credit exposure. |
| Accountant/CA | Reconciles subledger to General Ledger, reviews aging and audit evidence, and validates reporting periods. |
